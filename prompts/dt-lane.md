Work one ticket of feature "$1" in this lane. Ticket: $2. Start option: $3.

All ticket-start policy checks below are default safeguards, not unoverrideable limits. If $3 is exactly "override", the user explicitly requested it or accepted the extension’s start-warning confirmation: add `--override` to every `next` call below. Never invent that option. An override may bypass dependencies, `unsafe_with`, shared modules, saved blockers, plan gates, ticket ownership, checkout/dirty-tree checks and completed-work guards; it does not stop other agents, discard local files, bypass malformed data or the progress lock, or suppress native Git/API errors. Record the warnings; do not repeat a formal approval request.
The extension opens a picker for bare `/dt-lane` and supplies the chosen ID as $2. If no numeric ID was supplied, STOP and ask the user to run `/dt-lane`; do not automatically choose a ticket.
Use the lane claim owner from the injected session context for every `--owner` below. Do not invent or reuse another agent's owner.

## Ticket confirmation
The extension displays a short ticket summary and asks the user to confirm before this prompt reaches the agent, including explicit IDs, resumes and force takeovers. For a new T0/T1 project, the `/dt-approve plan` approve-and-start confirmation already authorizes starting ticket 00; the extension checks safety and displays its summary without asking again when there are no warnings. Treat that kickoff as confirmed and continue with Setup. Later resumes still require normal ticket confirmation. Normal confirmation chooses the ticket only and never approves a gate. A Start anyway confirmation explicitly authorizes the ticket-start policy override; it does not bypass malformed data, the progress lock or native Git/API errors. Unless an explicit non-interactive "override" was requested, if the extension did not show the summary and obtain confirmation, display only the ticket ID, title and a short outcome summary, then STOP to ask whether this is the ticket the user wants to start; do not claim, branch or implement until they confirm. `/dt-status <id>` displays a ticket without starting work.

## Setup
Before picking an explicitly named ticket, read its saved progress. Without an explicit override, if its PRs are all merged, do not resume/rebuild its branch: use `/dt-check-merged` to confirm the merge on GitHub and close it. Without an explicit override, if already accepted, report that and stop; do not suggest a status command.

T0/T1 features are one ticket (`00`) built in the current checkout on a `quick/<slug>` branch; `next` creates it without a worktree. Do not commit the feature folder on that branch.

1. Before touching any ticket code, run `node ~/.pi/agent/dt/dt.mjs next $1 --ticket $2 --owner <session-owner>` (add `--force` ONLY if $3 is exactly "force"). A claim is reserved atomically in progress.json before branching. Another owner is a refusal, even on the same branch. Force alone takes over only in the saved checkout; the separate confirmed --override option can bypass all ticket-start policy warnings, and neither option stops the old agent. Claims do not expire automatically; check the previous agent is gone before forcing. Read its output:
   - **resume**: this checkout is already on the ticket's branch. It prints the ticket's saved state (verified, todo, blockers, PRs, next): continue from `next`; do not redo finished steps.
   - **open pi in <path>**: a worktree was created for the ticket; tell me the path and STOP. I will open pi there and rerun this command.
   - a default refusal (active peer session, unavailable process inspection, claimed target ticket, blocked dependency, module clash, unsafe pair, dirty tree, wrong directory): report the warning and ask whether to start anyway. Continue only with explicit user override. Invalid data, failed Git/API operations or unavailable files require repair; do not silently discard data or bypass the progress lock.
   It prints the ticket file, the modules it touches, the overlay to read and the `checks` command.
2. Read ONLY: `spec.md` (T2: intended behavior, constraints and the shared Module map), the ticket, its linked UI references when applicable, the overlay, and the code of the modules in `touches`, including the supporting test and fixture files allowed below. Resolve `touches` keys through the spec's Module map, which defines concrete paths, responsibilities and module dependencies. Build ticket 00's interfaces from that map and the ticket's Scope; later tickets use the interfaces merged in 00 and earlier tickets. Ticket/lane ownership, work breakdown and landing order come from tickets; shared module definitions come from the spec. Backfill a missing map entry from known facts directly; ask about an ambiguous definition rather than inventing it. Read other affected ticket frontmatter and only necessary bodies when maintaining the plan.

Before UI implementation, read the ticket's UI reference section and open its linked screenshots and manifest, including for mixed UI/backend work. Follow its settled authority and agreed differences, not new behavior discovered on the live prototype. If references are missing or unreadable and there is no explicit user-approved waiver, save the gap as a blocker, release the claim and ask for screenshots or an explicit waiver, then update the editable planning references directly; do not silently invent or waive them. Planning screenshots in `references/ui/` are required inputs (unless explicitly waived), separate from optional implementation verification artifacts; preserve them.

## Questions
Ask only what blocks the next step and that neither the code nor the plan answers. Ask each as one numbered question with your recommended answer, in names I recognize (person, module), never bare IDs. Keep the claim and wait for my answer instead of stopping. A decision the plan already settled (for example which module owns a change) is not a question; follow the plan, and if the code contradicts it, describe the mismatch, ask only about an unsettled decision and update the editable planning files directly.

## Saving state
The next session knows only what the feature folder holds, so save the ticket's state with `node ~/.pi/agent/dt/dt.mjs progress $1 --ticket <id> --owner <session-owner> ...`. Each save replaces the previous one: it is the current state, not a log. Never edit progress.json by hand.
- When: after the scenarios fail for the right reason, after they pass, after verification, and whenever you stop, get blocked or hand over to me. Add `--release-claim` to the final save when handing work back or stopping. Normal session shutdown also releases this session's claims. Release does not mark the ticket done or make it available to `next`; resume that ticket explicitly in its saved checkout.
- What, one line each: `--next` the next concrete step; `--todo` what is left (repeat the flag, `--no-todo` when nothing is); `--blocker` what stops you (`--no-blockers` once cleared); `--verification` what passed, at which commit (`git rev-parse --short HEAD`), and what is not verified yet.
- PRs and issues created outside `dt.mjs pr` (an extra PR, a follow-up issue): `--pr <url>` and `--issue <ref or URL>`.
Code explains implementation details; keep the PR short. Save verification results, useful links, gaps and follow-ups as one-liners in progress.json through `dt.mjs progress --verification`, `--todo` and `--blocker`. Do not create a per-feature `evidence/` folder or separate verification logs by default. Save separate artifacts only when genuinely useful (for example, a screenshot for visual review), and link them in `--verification`. Preserve existing artifacts and their references; do not delete them as cleanup.

## Rules
Code, comments, test names, commit messages and PR titles/bodies must stand on their own. Never reference the dev-turbo plan, spec, tickets, slices or gates, or assume readers know the workflow. Describe current behavior and technical reasons, not which workflow step introduced something or will finish it. The same rule applies to documentation shipped with the change. Workflow references belong only in dev-turbo planning artifacts, saved progress and command/gate handovers; required issue links and concrete PR sequencing remain allowed.

- Public interfaces may change when the code needs it. If only this ticket and tickets that have not started depend on the change, make it, save `--todo "interface change: <one line>"`, and mention it in the PR. If merged code outside `touches` or another in-flight ticket depends on the old shape, STOP, save `--blocker "NEEDS INTERFACE CHANGE: <exact change>"`, and ask the user about the change and coordinate affected work before implementation; update editable planning files directly once settled.
- Keep production code inside the `touches` modules. Use other modules through their public interface only.
- Necessary tests, shared fixtures and test-only build wiring may be read and updated outside `touches` when required to verify the ticket outcome or keep mirrored fixtures synchronized. Do not block or request `/dt-revise` solely because these supporting files are outside `touches`. Do not weaken assertions, relax validation or change public contracts to make tests pass. Actual concurrent ownership conflicts still require coordination; this exception does not bypass lane claims or authorize unrelated production changes. Record the supporting paths and run their affected checks.
- Ports for anything slow or physical (network, hardware, clock); fakes live next to the port.
- Update `spec.md` and editable ticket files directly during normal work to reflect known facts, settled decisions and necessary implementation changes. Do not require a `/dt-revise` invocation. Keep done and merged tickets unchanged; extra work belongs in new or existing todo tickets. Coordinate changes affecting another active ticket before altering its scope, and record in-flight scope-change handovers through `dt.mjs`. Preserve the original plan approval and never use planning edits to bypass lane claims or add unrequested behavior. Never hand-edit progress.json: `dt.mjs` keeps the state.

## Investigation tickets
For a spike (a ticket with an **Investigation** section), keep normal claims, branching, review and merge closure. Replace the implementation loop's scenario-first and TDD steps with the ticket's bounded investigation: inspect the relevant code, run the agreed experiments or comparisons, and stop at the stated time or effort limit. Do not force a feature implementation or failing behavior test for a research outcome.

Write the short findings document at the repository path named by the ticket, with the question, evidence, alternatives and trade-offs, recommendation and remaining uncertainty. Retain only explicitly agreed experiment code; do not ship throwaway prototypes. Run applicable checks for retained files and save the findings link and summary in `--verification`; an inconclusive or negative result is not a failed spike when it meets Done when. Commit the findings so normal PR review and merge closure apply; do not claim the ticket done just because research stopped.

Do not choose an unresolved product decision or implement dependent work. After the findings are reviewed, update the editable planning files directly when the approach is settled; otherwise ask about the unresolved decision and save it in `--todo`. By default, dependent tickets remain blocked until the spike is closed and their unresolved approach is settled. An explicit start override can bypass that dependency warning, but it does not supply missing product decisions or justify inventing behavior.

## Loop
For implementation tickets:
1. Write executable scenarios for the ticket's Outcome and Done when, in the repo's native location (one per behavior, not per file). Run them: they must fail for the right reason. Save state.
2. TDD inside the module until the scenarios are green. Save state.
3. Verify per overlay (browser, device or build target). Save a short result and any useful links with `--verification`.
4. Run the `checks` command for the touched modules only.
5. Small commits; push the branch.

## Finish
1. Read `~/.pi/agent/dt/AGENTS.md` for the PR format. Write a short body to a temp file: `## Description` with a few plain bullets about what changed, then `## Testing` starting with exactly `unit tests + staging tests` and one suggested staging check. Add a simple bullet for a curl/browser check only if it was actually run. No test implementation, command dumps, test counts or unfinished work in the body; save pending checks in progress.json. Add a sequencing line only for specific PRs that must merge first. Preserve any description the user has edited. Do not edit or recreate existing published PRs for formatting.
2. Run `node ~/.pi/agent/dt/dt.mjs pr $1 <id> --owner <session-owner> --body-file <file>`: it opens the PR ready for review (`Closes #issue` when there is one), records it and moves the ticket to review with next `/dt-review <id>`. For ticket 00 of a T2 feature, add a small sequence diagram of the skeleton path to the PR description so the interfaces can be reviewed there.
3. Save the final state with `--owner <session-owner> --release-claim`: `--verification` and `--todo` (follow-ups and pending checks) or `--no-todo`.
4. Reply with at most 5 bullets: what was built, verification results, deviations (including interface changes), the one thing to look at, PR URL and whether it is ready for `/dt-review <id>`.
